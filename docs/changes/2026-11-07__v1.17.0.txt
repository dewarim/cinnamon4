Changes v1.17.0:

## Required migration step

This release changes the database schema, and a repository that has been running with Tika needs a
one-time cleanup on top of it. The DDL and the queries are in docs/migration.2026.adoc, section
v1.17.0. Apply them before starting the new server.

- database change: four columns are renamed - deletions.is_deleted to deleted, users.pwd to password,
  objects.state_id to lifecycle_state_id and lifecycle_states.copy_state_id to
  lifecycle_state_for_copy_id. A new tika_failures table records the objects whose Tika extraction failed,
  the unused index_jobs.update_tika_metaset column is dropped, and access_log.created becomes a plain
  timestamp. A repository that has been running with Tika also needs a one-time cleanup of the metasets the
  old error handling left behind - see docs/migration.2026.adoc, section v1.17.0, for the DDL and the
  queries. No API client sees any of this, but SQL you maintain yourself refers to the old column names.

## User facing: new endpoints for operators

- added: /api/admin/listIndexEvents reports what went wrong while indexing, newest first, with the
  message Lucene or the indexer produced. The server has been recording this in the index_events
  table since the Lucene indexer was written, and nothing could read it: index/info reports how
  many jobs failed, but an index job carries a failure count and no error text, so the reason a
  document is missing from the index was reachable by SQL alone. The request takes a limit (default
  100, at most 1000 - the rows carry exception messages, and the ones written for an uncaught
  exception in the index loop carry a whole stack trace) and an optional eventType: LUCENE is Lucene
  refusing a document, GENERIC a single item the indexer could not handle, ERROR an uncaught
  exception in the index loop, IO content that could not be read at all. Indexing only - a document
  Tika could not extract metadata from is indexed all the same, just without that metadata, and is
  reported by admin/listFailedTikaExtractions below.

- added: /api/admin/listAccessLog reports the requests that failed, newest first, with the request
  as it arrived, the error response that was sent back, the error code and the user who sent it.
  This is the access_log table, which every server with the default configuration has been filling
  all along - it is written for failed requests only, so it is the record of why clients are being
  refused. It, too, had no reader: the list statement threw until the read path was fixed, which is
  the last entry in this section. The limit defaults to 50 and cannot exceed 500, because every row holds a whole request body and
  a whole error response.

- added: /api/admin/listFailedTikaExtractions reports the objects whose Tika extraction failed, with
  the attempts made and the last error - the other half of "why is this document not searchable",
  since such a document is in the index but carries none of the metadata Tika would have extracted
  from its content. index/info reports the same failures through its own new
  listFailedTikaExtractions flag, which is capped at the thousand most recent rows: that flag
  answers "is anything wrong", while this endpoint is where the count can be followed up with a
  limit of the caller's choosing (default 100, at most 1000).

- added: all three endpoints live in a new servlet at /api/admin, and everything under that path requires
  superuser status - checked once for the servlet rather than per endpoint, so an endpoint added
  there later is closed by default. They are not on the resources they report about because they do
  not report about the repository: they report on the server's own operation, and the rows name
  objects by id and carry content paths, request bodies and exception messages for objects the
  caller may have no permission to read at all. Nothing was moved out of index/info to build them:
  its counts and its lists stay where they are.

- fixed: the access log can be read back. Its created column was a timestamptz, which the driver refuses to
  hand to the LocalDateTime property it belongs to, and the entry class had no constructor MyBatis could use
  - so AccessLogDao.list threw on both counts. Nothing in the server reads the access log, which is why
  neither showed up: a statement has to return a row before either can fail. The column is a plain timestamp
  now, like every other timestamp the models read, and the read path has a test.

## User facing: Tika extraction

- fixed: a Tika server that answers with an HTTP error no longer makes the document unindexable for good.
  The error was turned into metaset content ("tikaFailedToParse"), and since the Tika service looks for
  objects that have no tika metaset, that counted as a finished extraction and the document was never
  offered again. A Tika server that starts rejecting a content type after an upgrade, or a wrong baseUrl,
  therefore wrote off everything it was handed, silently and permanently: nothing reported it, and no API
  call could undo it. Such a rejection is now an error rather than a result, and the document stays in the
  queue. Which failures the document pays for is decided by the status: Tika answers 400, 413, 415 or 422 for
  content it will not take, and 500 when a parser throws on it, so those count against its attempts, while
  401, 403, 404, 408, 429, 502, 503 and 504 are what a restarting server, a wrong baseUrl or a proxy in front
  of Tika answers to every request alike and are not counted at all. Otherwise an outage would still write
  off the whole backlog, just visibly instead of silently. A server that cannot be reached is treated the
  same way and always was: it says nothing about the document, so it is retried indefinitely. Such a retry
  opens the content again for every attempt instead of re-sending what is left of the stream the failed
  attempt consumed: that would have uploaded a truncated document under the original length, and Tika
  answering 200 to half a file would have stored metadata for a document nobody has.

- fixed: the Tika service survives a failed pass. Its loop had nothing catching an exception from the pass
  itself, so one object pointing at a format row that no longer exists ended the thread for the lifetime of
  the server - with no log line saying so, and no document extracted again until a restart. A failed pass now
  costs a pause, an object whose format is gone is counted as a failure of that object, and the metaset type
  is looked up inside the pass so that a database that is briefly unavailable at startup no longer leaves the
  service dead. Relatedly, the loop skips its pause only after a pass that actually extracted something: it
  used to skip it whenever the queue handed it a full batch, which during an outage is every single pass, so
  the service hammered an unreachable Tika with no pause at all for as long as the outage lasted.

- added: the objects whose Tika extraction failed are recorded in a new tika_failures table with their
  attempt count and the last error, and reported by index/info - the new listFailedTikaExtractions flag
  returns the list, and the count is always included. Listing them requires superuser status, which the rest
  of index/info does not: the rows carry the error text Tika or the content store produced, which includes
  content paths and exception messages for objects the caller may have no permission to read. The list is
  also capped at the thousand most recent rows - the table has one row per object at worst, so an unbounded
  list would be a request that renders the repository into one XML document; the count tells a client whether
  it is looking at all of them. Without the record there was no way to find out that a
  document has no Tika metadata, because the document itself is indexed and searchable. A document is given
  up on after maxTikaAttempts tries (new in cinnamonTikaConfig, default 3) instead of being retried on every
  pass of the service forever, which is what used to happen to an object whose content file was missing.

- changed: the retryDelayInSeconds and maxRetryDelayInSeconds settings of cinnamonTikaConfig are now actually
  read - the retry policy had the defaults hard-coded - and a configuration that cannot work is reported and
  replaced by the default rather than taken literally: a delay of zero or less is what failsafe rejects with
  an IllegalArgumentException naming neither the setting nor the file, thrown out of server startup, and a
  maxTikaAttempts of zero reads like "no limit" while meaning that the first failure writes a document off
  for good. Such a value is now logged with the name of the setting and the default used in its place. A
  configuration that leaves no room to back off retries at a constant delay, as before.

- fixed: reindex honours updateTikaMetaset again. The flag has been part of the request, validated and
  documented, since the Tika service became asynchronous in v1.6.8, and has been ignored for just as long -
  there was no way left to ask for a fresh extraction. It now deletes the tika metasets of what the request
  names - the objects it lists, plus the content of the folders it lists, and the whole repository only for a
  full reindex - and forgets their recorded failures, which is what puts the documents back in the extraction
  queue; the response says how many metasets were deleted. This is also the recovery
  path after a Tika server was broken or a content store was unmounted.

- fixed: replacing the content of an object with setContent deletes its tika metaset, so the metadata is
  extracted from the new file. Without that the object kept the metadata of the file it no longer holds -
  indexed, searchable and wrong - because nothing revisits an object that already has a tika metaset. The
  other paths that replace content already did this (copyToExisting) or create a new object that has no
  metaset to begin with (create, version, copy).

## User facing: configuration

- added: luceneConfig.truncateIndexEventsAfterRow (default 1000) and
  luceneConfig.truncateIndexEventsBy (default 100) prune the index_events table, the way
  loggingConfig.truncateLogAfterRow has always pruned the access log: once the table holds more rows
  than the first setting, the oldest rows of the second setting's number are deleted. The table had
  no retention at all, and one unindexable document writes a row per attempt per pass of the index
  service, so a server that nobody watches could grow it without limit. Pruning runs right after
  events have been written, so the row count is only read when something was added to it. Setting
  truncateIndexEventsAfterRow to zero or less switches pruning off and keeps every event, which is a
  choice an operator can make; a truncateIndexEventsBy of zero or less would delete nothing, so it
  is logged and replaced by the default.

- fixed: luceneConfig.logFailedAttemptsToDb is read. It is documented as "if true, store failed
  index jobs in index_events table", has defaulted to true since it was added, and was read by
  nothing at all - the events were written whatever it said. Setting it to false now does what it
  says, which also switches off what admin/listIndexEvents reports; the default is unchanged, so a
  configuration that does not mention it behaves as before.

## Internal improvements

- changed: column names are mapped by convention rather than declared one by one. MyBatis'
  mapUnderscoreToCamelCase setting is enabled, so content_hash reaches contentHash without a line saying so,
  and the mappers went from 35 resultMap declarations holding 169 mapping lines to 4 holding 7. Two of the
  maps that went existed only because a statement gave a computed column a name of its own: those now alias
  the column after the property ("as path" in getFolderPaths, "as head_id" in rootAndLatestHead), one held
  nothing but the primary key of a column already called id, and four more were retired by renaming the
  column in the database (see the migration entry above). The four that remain are the exceptions that cannot
  be renamed away: osd_id and folder_id to objectId, where one Meta class serves two tables and links carries
  both columns on purpose, and is_unique to unique, where the column cannot take the property's name
  because unique is a reserved word. Nothing on the wire
  changed and no query changed its result: a resultMap always took precedence over auto-mapping, so enabling
  the setting on its own was a no-op, and every deleted declaration listed exactly what the convention now
  derives. Note that MyBatis matches column names case-insensitively, which is why formats.contenttype
  reaches contentType and index_items.fieldname reaches fieldName with no declaration at all.

- fixed: getGroupsOfUserById selected every column of both joined tables, and groups and group_users each
  have an id column, so the result set carried two columns of that name and which one filled Group.id
  depended on the order the driver reported them in. It selects only the groups columns now. Found by the
  test-run strictness described under Testing below; the statement is exercised by no test, so this was
  caught by reading the mappers against the schema rather than by a failure.

- fixed: the update statement of the deletions table selected on an id column, which that table does not
  have - its key is osd_id, and Deletion.getId() returns exactly that, so the statement looked healthy and
  would have failed against Postgres. Nothing calls DeletionDao.update today, which is why it never showed:
  the strictness described under Testing below only covers statements a test actually runs, so this came from
  reading the mappers against the schema. The statement selects on osd_id now and no longer sets the key it
  selects on.

- fixed: statements over four tables no longer select columns their model cannot hold. The sessions table
  carries username and ui_language_id, and folder_types and object_types each
  carry a config column that no mapper or model mentions; all were being fetched and thrown away. Those
  statements list their columns explicitly instead. No behaviour change - the values were already discarded -
  but selecting them made the tables and the models look like they agreed when they do not.

- changed: AccessLogMapper lost a resultMap that no statement referenced. Its one select already named a
  result type, so the declaration had been dead since it was written. The access log uses a second MyBatis
  session factory with its own configuration file, which got the same two settings as the main one so the two
  cannot drift apart.

- fixed: the set of paths whose request body is not logged is assigned where it is declared. It was a static
  field assigned from an instance initializer, so it was re-assigned on every construction - which, now that
  the access log can be read, means once per row from whichever thread is reading. The constructor the read
  path needs is what exposed it.

- changed: removed what was left of the synchronous Tika path, all of it unreachable since v1.6.8: the
  index_jobs.update_tika_metaset column (never written, and no property on IndexJob), the third parameter of
  OsdDao.updateOsd, which the method body ignored, and the local flag the version endpoint computed to pass
  to it. The lookup of the tika metaset type lives in MetasetTypeDao now instead of being spelled out in
  three places.

- fixed: an object whose content cannot be read is recorded as an IO failure rather than a generic
  one. IndexEventType.IO existed from the start and was written by nothing: a content file that is
  gone, or a content store that is not mounted, threw inside the indexer and came out of the outer
  catch as GENERIC, which is also what a document the indexer cannot handle produces. The job is
  counted as failed exactly as before and the message is the same; only the type now distinguishes
  "this document is a problem" from "the content store is a problem", which is the distinction an
  operator reading admin/listIndexEvents needs first.

- changed: IndexEventType has no TIKA value any more. It was written by nothing, and a failed Tika
  extraction is not an index event: the document is indexed, and the failure is recorded per document
  in tika_failures with its attempt count, cleared as soon as an extraction succeeds. Keeping the
  value made admin/listIndexEvents look as though it could answer a question that belongs to
  admin/listFailedTikaExtractions. No row ever carried it, so nothing in any database has to change.

- changed: AccessLogEntry.created and IndexEvent.localTime are rendered as timestamp strings rather
  than as an array of numbers. Both classes are new on the wire with this release - a LocalDateTime
  without the format annotation that every other date in the API carries goes out as seven separate
  elements, which no client can read back.

- changed: the insert and update statements of IndexEventMapper declared parameterType Acl, which
  they inherited from whichever mapper they were copied from. MyBatis treats the declaration as
  advisory and mapped the properties by name regardless, so nothing was wrong at runtime; the
  statements name IndexEvent now.

## Testing

- added: the test run fails when a statement selects a column that the result type has no property for,
  instead of dropping it silently. That is MyBatis' autoMappingUnknownColumnBehavior, set to FAILING through
  a system property that surefire passes and DbSessionFactory reads. Production leaves it at NONE on purpose:
  over a hundred statements select every column of their table, so FAILING there would turn a migration that
  adds a column into failing reads until the model caught up. Under NONE the behaviour is exactly what it has
  always been, which is what makes the strictness safe to confine to the build. It only covers statements a
  test actually runs, which is why the two mapper bugs above were found by reading the mappers against the
  schema instead.
