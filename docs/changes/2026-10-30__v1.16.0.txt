Changes v1.16.0:

- changed: request validation is now driven by constraint annotations (Jakarta Bean Validation, implemented by
  hibernate-validator) instead of a hand-written validated() method per request class. Every request still answers
  with the same error code it did before, INVALID_REQUEST, but the error message now lists every field that was
  wrong, by name and - for a list payload - by index, for example "links[0].aclId must not be null". Messages are
  rendered in the requesting user's uiLanguage where hibernate-validator ships that language, English otherwise.
  Nothing on the wire changed: no request or response gained, lost or renamed an element, and docs/api.md is
  byte-identical. The constraints live on the request records and on the model classes the requests carry (Acl,
  Folder, UserAccount, ...), where they are checked only when a request cascades into them with @Valid, not as
  invariants of the class. A rule no annotation can express - "a link points at a folder or at an object", "an
  account update has to name at least one field to change", "a relation search has to be narrowed by at least one of
  its three id lists" - is still hand-written in validated(), which stays as the documented escape hatch.

- fixed: a create, update or delete request with an empty payload is now rejected instead of being accepted and
  handed to the servlet. Most of the hand-written checks tested the payload with allMatch or noneMatch, and both are
  vacuously true for an empty collection, so an empty body passed validation. What happened next depended on the
  endpoint: usually an empty response, sometimes a confusing later error. Affected every create, update and delete
  request; the ones with an explicit emptiness check (a minority) are unchanged. A unit test now walks UrlMapping and
  asserts the whole set, so a request added later cannot reopen the hole.

- fixed: createRelation accepted a relation whose rightId or typeId was not positive. The check read
  "leftId <= 0 || rightId <= 0 && typeId <= 0", and && binds tighter than ||, so a non-positive rightId alone - or a
  non-positive typeId alone - passed. All three ids are now required to be positive.

- fixed: updateLink with an owner id of null answered 500 instead of 400. Link.validated() null-checked aclId but
  then unboxed ownerId, so a link without an owner threw a NullPointerException inside validation.

- changed: id fields that were documented as positive are now rejected when zero, where before the request passed
  validation and the lookup behind it answered "not found". updateOsd accepted zero for parentId, ownerId, aclId,
  typeId and languageId (its check read ">= 0"); listAclGroups accepted an aclGroupId or groupId of zero as long as
  an idType was given. Both now answer INVALID_REQUEST, naming the field. No id in the database is ever zero, so no
  request that used to succeed is affected.

- added: an OSD insert now checks that owner, creator and modifier are present before writing the row, and answers
  OBJECT_IS_MISSING_MANDATORY_USER instead of letting the not-null constraint fail as a database error. All three
  are set by every caller; the check is there so a new call path cannot quietly reach the database without them.

- changed: docs/api.md is regenerated by the dist build, from the UrlMapping enum and the examples() of the
  request/response classes, so the checked-in API documentation cannot drift from the code. It is written by
  "CinnamonServer --write-api <file>"; "--api" prints the same document to stdout. Both renderings are
  deterministic, so two consecutive builds produce byte-identical files.
