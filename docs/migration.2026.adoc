=== v1.16.0

Two separate things changed about the search index in this release: Lucene was upgraded from 9.12.1
to 10.6.0, and the text analyzer changed. They have different consequences, so they are described
apart.

==== The index format: no action required

Lucene 10 uses a new index format and cannot read a Lucene 9 index on its own. The server ships
`lucene-backward-codecs`, so it does not have to: an existing index is read as before, new documents
are still written to it, and its old segments are rewritten in the current format as Lucene merges
them. Nothing has to be stopped, deleted or rebuilt for the upgrade itself.

==== The analyzer: reindex if the repository holds CJK or full-width text

A document keeps the tokens it was indexed with. Lucene analyzes text when a document is added and
never again - merging segments copies already-inverted data, it does not re-run the analyzer - so
documents indexed by an earlier version keep the tokens `StandardAnalyzer` produced, while queries
are now analyzed by `CinnamonAnalyzer`. Where the two disagree, old documents stop being found.

For Latin text they do not disagree: `CinnamonAnalyzer` is `StandardAnalyzer` plus two CJK filters,
and `CinnamonAnalyzerUnitTest` asserts that both produce identical tokens for Latin input. A
repository without CJK or full-width content therefore needs no reindex for correctness.

It matters in three cases:

* *CJK text.* `液压泵` was indexed as the three tokens `[液, 压, 泵]`, because the tokenizer follows
  UAX#29 and emits one token per Han character. Queries now produce the bigrams `[液压, 压泵]`, which
  do not match the old tokens. CJK documents indexed before this release will not be found by the
  new queries until they are reindexed - note that this is the same change that makes CJK search work
  at all, so for those documents a reindex is what delivers the fix.
* *Full-width Latin.* A document containing `ＡＢＣ－１２３` is now folded to `abc-123` at index time,
  so a search for `ABC-123` finds it. Documents indexed earlier kept the full-width form and are
  only reachable by searching in full width.
* *Turkish, Azeri or Lithuanian server locale.* Object names and folder paths were lowercased with
  the machine's default locale, so `I` was indexed as the dotless `ı`. That is fixed, and a reindex
  corrects the affected tokens. (Installations on any other locale are unaffected: across every
  Unicode codepoint and all 245 languages the JVM knows, only those three lowercase differently.)

==== Performance: reindex recommended

Independently of correctness, two improvements only apply to documents that have been reindexed:

* The search rework reads object ids from a `NumericDocValuesField`, which older documents do not
  have. A stored-field fallback keeps them working, so this is a speed difference rather than a
  functional one.
* Only segments in Lucene's current format benefit from the new format's encoding work.

==== How to reindex

It can be done while the server is running:

    POST /api/index/reindex

Reindexing a large repository affects performance while it runs, so pick a quiet window - on a
machine with slow storage this is I/O bound and can take a long time.

*Check one setting first.* `maxIndexableContentSizeMB` (new in this release, default 2048) caps the
content size the indexer will read. A document whose content was indexed before that cap existed
becomes metadata-only when it is reindexed: still findable by name and metadata, but its content is
no longer searchable, with a warning naming the object and both sizes in the log. Raise the limit, or
`maxIndexableContentPercentOfHeap`, before reindexing if any content exceeds it.

If you would rather start from an empty index: stop the server, delete the directory configured as
`indexPath` in `luceneConfig` (default `/opt/cinnamon4/cinnamon-data/index`), start the server and
reindex. Searches return nothing until the reindex has caught up, so this is the one variant that
needs a maintenance window.

=== v1.15.1

Every OSD must have an owner, as folders and links already do. Before applying the change,
check for OSDs without one:

    select id from objects where owner_id is null;

If there are any, give them an owner first, for example the admin user:

    update objects set owner_id = <id of admin> where owner_id is null;

Then:

    -- SQL
    alter table objects alter column owner_id set not null;

=== v1.17.0

Tika extraction now keeps a record of the documents it could not handle, which needs one new table:

    -- SQL
    create table tika_failures
    (
        osd_id       bigint    not null
            constraint tika_failures_pkey primary key
            constraint tika_failures_osd_id_fkey references objects on delete cascade,
        attempts     int       not null default 1,
        last_attempt timestamp not null default current_timestamp,
        last_error   text      not null
    );

The `index_jobs.update_tika_metaset` column has been unused since tika indexing became
asynchronous in v1.6.8 - nothing has written it since, and the model does not carry it:

    -- SQL
    alter table index_jobs drop column if exists update_tika_metaset;

The `created` column of `access_log` becomes a plain `timestamp`, like every other timestamp column
the models read. As a `timestamptz` the driver refuses to hand it to the `LocalDateTime` property it
belongs to, so reading the access log threw - which nothing in the server did, which is why it was
never noticed:

    -- SQL
    alter table access_log alter column created type timestamp;

Existing values are converted to the database server's local time, which is what new rows have been
getting from the column default all along. Nothing in the application reads the column's offset.

==== Four columns are renamed

Column names are mapped onto properties by convention (MyBatis' mapUnderscoreToCamelCase), and these
four were the ones that did not fit, each costing a hand-written mapping. Renaming them removes the
last of those declarations that could be removed:

    -- SQL
    alter table deletions rename column is_deleted to deleted;
    alter table users rename column pwd to password;
    alter table objects rename column state_id to lifecycle_state_id;
    alter table lifecycle_states rename column copy_state_id to lifecycle_state_for_copy_id;

Nothing an API client sees changes - the property names were always `deleted`, `password`,
`lifecycleStateId` and `lifecycleStateForCopyId`, and only the column names catch up. But any SQL
you maintain yourself - reports, integrations, backup or migration scripts, a BI tool reading the
schema - refers to the old names and has to be updated. `objects.state_id` in particular was the
object's *lifecycle* state, which is what the new name says.

Three mappings remain and are not worth renaming: `osd_meta.osd_id` and `folder_meta.folder_id` are
read into one shared Meta class, so no single column name fits both; `links` carries `osd_id` and
`folder_id` as a deliberate pair; and `metaset_types.is_unique` cannot be renamed at all, because
`unique` is a reserved word in Postgres.

==== If this repository has been running with Tika

Until now, a Tika server that answered with an HTTP error produced a metaset with the content
"tikaFailedToParse" instead of metadata. That metaset counted as a successful extraction, so the
document was never offered to Tika again. Those documents have to be unblocked once, by hand:

    select count(*) from osd_meta
    where type_id = (select id from metaset_types where name = 'tika')
      and content like '%tikaFailedToParse%';

If that count is not zero, delete the rows - the documents are then extracted again on the next
pass of the Tika service:

    delete from osd_meta
    where type_id = (select id from metaset_types where name = 'tika')
      and content like '%tikaFailedToParse%';

From this release on, a rejected document is recorded in `tika_failures` rather than being written
off silently: it is retried until `maxTikaAttempts` (new in `cinnamonTikaConfig`, default 3), and
`index/info` reports the ones that were given up on - its `listFailedTikaExtractions` flag and the
`admin/listFailedTikaExtractions` endpoint both return them with their attempt count and the last
error. A Tika server that cannot be reached at all is not counted
against any document and is retried indefinitely, so an outage no longer costs anything.

To make Cinnamon extract documents again - after fixing a broken Tika server, or remounting the
content store - call `index/reindex` with `updateTikaMetaset` set to true. That deletes the tika
metasets of the named objects (all of them, for a full reindex) along with their failure records,
which is what puts the documents back in the queue. The flag was accepted but ignored between
v1.6.8 and this release.
